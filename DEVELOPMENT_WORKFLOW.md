# Рабочий цикл разработки TaskFlow

## Размер пакета
Один пакет — не более 1–3 небольших задач. Большие задачи делятся на этапы с отдельными критериями приёмки. Не пытаться выполнить весь проект одним длинным запросом.

## Перед работой
1. Прочитать DEVELOPMENT_STATE.md, TASKS.md и последние записи CHANGELOG.md.
2. Проверить GitHub branch, HEAD commit и наличие файлов.
3. Проверить активные browser/terminal operations. Если операция pending/running, продолжать проверять тот же run ID, не запускать дубликат.
4. Выбрать 1–3 ближайшие задачи и определить результат и способ проверки.

## Во время работы
- Вносить только изменения, относящиеся к выбранным задачам.
- Не смешивать несвязанные изменения и не менять существующие файлы без необходимости.
- Не публиковать токены, пароли, приватные ссылки и пользовательские данные.
- Не подключать платные тарифы, БД или API без явного согласования.
- При ошибке сначала диагностировать текущее состояние, не повторять запись вслепую.

## После работы
1. Запустить синтаксические, структурные, unit или manual checks.
2. Проверить путь, branch и commit каждого нового/изменённого файла в GitHub.
3. Обновить TASKS.md и добавить подтверждённую запись в CHANGELOG.md.
4. Обновить DEVELOPMENT_STATE.md: что сделано, что проверено, что осталось и следующая задача.
5. Сохранить изменения и журнал в GitHub.

## Восстановление после тайм-аута
GitHub main — источник истины для опубликованных исходников. Локальная папка может быть устаревшей или содержать неопубликованные изменения. Сверить GitHub commits и файлы с журналом, проверить активные операции и продолжить с первой незавершённой задачи.

## Границы автономности
Этот механизм сохраняет контекст между запросами, но не превращает чат в бесконечно работающий фоновый процесс. Работа выполняется в активных запусках, пока подключённые инструменты и компьютер доступны.
